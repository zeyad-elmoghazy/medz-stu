## 5 · Two parallel quiz-taking systems — both real, both intentional

There are two separate, fully independent quiz-taking routes in the app right now. **This is not a duplicate-code bug — do not delete either one without reading this first.**

1. **`/student/quiz/[subjectId]`** (`app/(student)/student/quiz/[subjectId]/page.tsx`, ~1740 lines) — the original, feature-rich engine: AI tutor panel, notes editor, bookmarks, mistake-practice mode. It sources questions **exclusively from a static bundled file**, `data/histology-questions.ts` (11 hardcoded Histology questions) — it never touches the database or any API route for question content, regardless of what `[subjectId]` is in the URL. This is what every existing entry point in the app still points to (dashboard's two quiz buttons, the results page, the exam generator) — all of them hardcode the literal path `/student/quiz/histology`.
2. **`/student/quiz/chapter/[chapterId]`** (`app/(student)/student/quiz/chapter/[chapterId]/page.tsx`, ~330 lines) — a new, minimal, **DB-backed** engine built this session. It fetches real published questions for one chapter via `GET /api/student/chapters/[chapterId]/questions` (`status='published'` filtered explicitly in the query, not just relied on via RLS). No AI tutor, no notes, no bookmarks — just question → choices → submit → explanation → next, with a real backend behind it. The Catalogue's chapter rows link here via a "Start Quiz" CTA, but **only when a chapter's `published_count > 0`** — which right now is **zero chapters**, so this CTA is currently invisible everywhere in the live app (confirmed correct behavior, not a bug — nothing is published yet).

**Why both exist**: the static engine has real, richer functionality (AI tutor, notes, bookmarks) that took real effort to build and that nothing has replaced yet. The new one proves the DB-backed pipeline end-to-end (publish → chapter-scoped delivery → real quiz) without touching or risking the working static path. Migrating the static engine's rich features onto the DB-backed data source is explicitly **not done** — that would be the natural next step if this becomes the primary quiz surface, but nobody has started it.

- The entire legacy Subjects route tree (`student/subjects/page.tsx` and its `[subjectId]`/`[subjectId]/[moduleCode]` children) — superseded by the Catalogue, redirected via `next.config.js` (`/student/subjects/:path*` → `/student/catalogue`, `307`).
- DB: `get_professor_stats()` RPC, the `professor_own_jobs` and `flags_professor_manage` RLS policies, both `professor_id` columns (`modules`, `questions`), and the `jobs`/`upload_jobs` tables themselves.
- `'professor'` removed from `lib/demo-profile.ts`'s `UserRole` type (cosmetic — demo mode is client-side-only and never touched the real DB, whose `CHECK` constraint already excluded `'professor'` from the pivot).

**What was renamed instead of deleted, and why it matters**: `upload_jobs_prof_own` → `upload_jobs_admin_own` (migration `023`). This policy's `qual` (`professor_id = auth.uid()`) looked professor-scoped by name, but it was actually what let `app/api/admin/content/upload/route.ts` write its own rows into `upload_jobs` — that route runs on the RLS-bound client (not service-role), and sets `professor_id: user.id` to the *admin's own id*, so this ownership-style check was genuinely load-bearing for a real, currently-used feature (PDF/OCR content extraction). It was renamed, not dropped, specifically to preserve that. **This was caught before applying the migration**, by reading the actual consuming route, not by trusting the policy's name.

One layer deeper, in a **later, separate** pass (migration `024`): the whole `upload_jobs` *table* turned out to be safe to drop anyway — not because the ownership check was wrong, but because nothing ever read the table back (no polling route survived, the admin upload wizard only uses the direct POST response, and the same "content uploaded" event is already mirrored into `activity_log`). So the rename in `023` and the table-drop in `024` aren't contradictory — `023` correctly identified the *policy* as load-bearing at the time, and `024` established, independently and later, that the *entire mechanism* the policy protected was redundant once you looked at what actually consumed it, not just what wrote to it. If this reads as confusing revisionism, it isn't — it's two different, narrower questions asked at two different times, both answered correctly for what was asked.

**The general lesson, worth internalizing for any future schema change on this codebase**: dependency-checking before a `DROP` needs to cover more than formal FK constraints. The actual dependency check that mattered here was reading application code that queries these columns/tables through `untypedFrom(supabase)` — a helper used almost everywhere in this codebase specifically *because* it bypasses the generated `Database` type's compile-time column checking (documented reason: `auth-helpers-nextjs@0.8` collapses the type to `never` under chained builders). That means:
- `next build`'s TypeScript pass will **not** catch a dropped column/table still being selected or inserted somewhere — confirmed directly this session: three real admin routes broke at runtime after `024` and the build stayed green throughout.
- The only way to know for certain is either an exhaustive grep for every column/table name across `app/`/`lib`/`components` (not just FK-adjacent files) **or** actually running the routes' real queries against the live DB after the change.
- This session did the second one *after* the break was already live in production, not before — three routes (`api/admin/content/overview`, `api/admin/content/questions`, `api/admin/questions/import`, plus `api/admin/content/upload`'s `upload_jobs` writes) were broken for some window of real time before being caught and fixed in the same sitting. All four are fixed and re-verified now (§1), but the process gap that let it happen is real and should inform how the next schema change on this project gets scoped — see §7 for the standard this now sets going forward.

## 7 · Verification standards this project now expects

Established (sometimes the hard way) over the course of this engagement — apply all of these to any future change, not just the ones that happened to trigger them:

1. **Fresh-fetch SHA confirmation on every push.** Never trust `git push`'s exit code alone. After every push: `git fetch origin`, then explicitly compare `git rev-parse HEAD` against `git rev-parse origin/<branch>`. This document itself was verified this way.
2. **Dependency checks before any schema change must cover more than FK constraints.** A `DROP TABLE`/`DROP COLUMN` dependency check needs, at minimum: (a) formal FK constraints, (b) informal/column-level references (a column named e.g. `job_id` with no declared FK), (c) views, (d) triggers, **and** (e) actual application code reading or writing the object — grepped across the whole app, not assumed safe because the schema-level check came back clean. §6 is the concrete example of why (e) is not optional: the schema-level check for the `jobs`/`upload_jobs` drop was completely clean, and three live routes broke anyway.
3. **`untypedFrom()` (and any pattern like it) is a compile-time blind spot, not just a typing inconvenience.** On this codebase specifically, assume `next build` passing tells you nothing about whether a query against a changed table/column still works. The only real verification is running the actual query — either through the live app, or (when no login credentials are available, which is the norm in this environment) by replicating the exact query shape via direct SQL against the target database, explicitly disclosed as SQL-replication rather than a live HTTP round-trip. Several verifications this session went further and simulated real RLS enforcement (via `SET LOCAL ROLE authenticated` + `SET LOCAL request.jwt.claims`) rather than relying on a superuser-bypassing connection, specifically to catch cases where a policy rename or logic change silently broadened or narrowed access — worth doing for any future RLS-adjacent change.
4. **Binary assets are transport-only in this repo, never committed as source.** Large files (reference-page images, PDFs used for one-off imports) get moved into the repo only long enough to be a stable path for a script to read from — they get uploaded to real storage (or, if the upload step hasn't happened yet, simply left on disk) and excluded from git via `.gitignore`, never committed. This session's `.gitignore` update (`scripts/import/reference-pages/`, `scripts/import/*.png`) is the concrete pattern: cover both the intended directory layout and whatever flat pattern a batch actually used, and confirm via `git status --porcelain` / `git check-ignore -v` that the files are genuinely invisible to git, not just manually left out of one commit.
5. **Test-data insert/delete cycles against MediZee need a cleanup+re-verify step every time**, not just "delete and assume it worked." Every insert this session that used MediZee as a scratch space for verification was followed by an explicit `DELETE` and then a fresh `SELECT count(*)` to confirm the table returned to its prior baseline — not just a claim that cleanup happened.

## 8 · Rebrand (MedZ → MediZee) — completion status

**Complete, re-verified fresh for this document.** Palette: Deep Navy `#0B1F33`, Medical Teal `#00A6A6`, Soft Mint `#D9F3F0`, Off White `#F7F9FA`, Slate `#536477`, plus derived tints Teal-glow `#33BFBF`, Navy-light `#132B45`, Slate-light `#8B98A6`. No remaining bare "MedZ" brand text in user-facing code (the only grep hits left are comments referencing the *database project name* `MedZ-Stu`, which is a separate, correct historical reference — not a missed rebrand spot). No remaining Tailwind `violet-*`/`purple-*` utility classes anywhere in `app/`/`components/`. The one remaining `#7C3AED`/`#8B5CF6` pair (`components/admin-content/AdminOverviewPanel.tsx`'s DAU-chart gradient) is a deliberately-excluded functional/status color, not a miss — documented as such in that file.

**The lesson worth naming explicitly, since it happened twice in different forms**: the rebrand needed two genuinely different search methodologies to reach full coverage, and the first pass's "done" was wrong in a way that only a second, differently-shaped search caught.
- **Round 1 — hex-string gradients.** The first automated substitution pass searched for and replaced literal hex color strings. It had a real bug: it mapped two *different* source purples (`#7C3AED` and `#8B5CF6`) both to the *same* single target teal, which silently collapsed roughly 50 two-stop CSS gradients (`linear-gradient(135deg,#7C3AED,#8B5CF6)`) into flat single-color backgrounds — a visual regression a hex-string diff wouldn't obviously flag as wrong, since both colors technically got "replaced." Caught, reverted, and re-done with a gradient-aware script that maps two-stop pairs to a proper two-tone replacement instead of collapsing them.
- **Round 2 — Tailwind named utility classes.** After the hex-string pass was confirmed clean, a **separate**, later grep for Tailwind color-utility class *names* (`text-violet-500`, `bg-purple-600`, etc.) found 31 more lines across ~9 files that the hex-string search structurally could not have found, because these use Tailwind's named-palette classes, not inline hex values or CSS custom properties — there was no hex string in the source for the first search to match against. Fixed in a dedicated pass (commit `d4de867`, currently `main`'s HEAD).

  **The transferable lesson**: "search for the brand's old hex codes" and "search for the brand's old *framework-native* color tokens" are two different search problems that don't overlap, and clearing the first doesn't imply the second is clear. Any future color/brand audit on this codebase (or a similar one using both inline styles and Tailwind) needs both passes run independently, not just one exhaustive-feeling pass.
